## 2. DOMAIN ANALYSIS

### General Field of Business

The project operates within the **Healthcare Information Systems** domain, specifically focusing on hospital administration, patient management, and clinical workflow optimization. This domain encompasses the digitization and automation of healthcare delivery processes across multiple medical facilities.

### Terminology and Glossary

| Term | Definition |
|------|------------|
| **Patient** | Individual receiving medical care and treatment |
| **Healthcare Provider** | Medical professional (doctor, nurse, specialist) delivering care |
| **Appointment** | Scheduled meeting between patient and healthcare provider |
| **Consultation** | Medical examination and diagnosis session |
| **Medical Record** | Documentation of patient's health history, diagnoses, and treatments |
| **Prescription** | Written order for medication or treatment |
| **Surgery** | Medical procedure involving operative intervention |
| **Surgical Team** | Group of medical professionals participating in surgery |
| **Consent Form** | Legal document authorizing medical procedures |
| **Medical Condition** | Disease, disorder, or health issue affecting a patient |
| **Specialization** | Area of medical expertise (e.g., Cardiology, Neurology) |
| **Admission** | Process of entering a patient into hospital care |
| **Discharge** | Process of releasing a patient from hospital care |
| **EHR (Electronic Health Record)** | Digital version of patient's medical history |
| **Triage** | Process of determining priority of patient treatments |
| **Ward** | Hospital division for specific patient care |
| **Outpatient** | Patient receiving treatment without overnight stay |
| **Inpatient** | Patient admitted for overnight hospital stay |

### Understanding of Business Environment

Healthcare facilities operate in a complex, highly regulated environment characterized by:

- **24/7 Operations**: Continuous patient care requiring round-the-clock staffing
- **Multi-disciplinary Teams**: Collaboration between doctors, nurses, specialists, and administrators
- **Regulatory Compliance**: Adherence to health regulations, patient privacy laws (POPIA in South Africa)
- **Critical Decision Making**: Time-sensitive medical decisions affecting patient outcomes
- **Resource Management**: Efficient allocation of beds, equipment, and personnel
- **Financial Complexity**: Insurance claims, billing, and payment processing
- **Data Sensitivity**: Strict confidentiality and security requirements for patient information
- **Quality Assurance**: Continuous monitoring of care standards and patient safety

## 3. DEFINE THE PROBLEM

### Primary Problem Statement

South African hospitals and medical facilities face significant operational inefficiencies due to fragmented, paper-based systems and lack of integrated digital solutions. This results in:

1. **Patient Safety Risks**
   - Medical errors due to incomplete patient history access
   - Difficulty in identifying drug allergies and interactions
   - Delays in emergency treatment due to information retrieval challenges

2. **Operational Inefficiencies**
   - Average 45-60 minutes wasted per day per doctor on administrative tasks
   - 30% of appointments result in scheduling conflicts or no-shows
   - Duplicate data entry across different departments
   - Lost or misfiled patient records (15-20% of paper records)

3. **Poor Resource Utilization**
   - Bed occupancy rates below optimal levels due to poor tracking
   - Surgical theater underutilization (30-40% downtime)
   - Staff overtime costs due to inefficient scheduling
   - Medical supply wastage and stock-outs

4. **Limited Accessibility**
   - Patients cannot easily access their medical history
   - Doctors lack real-time patient information during consultations
   - Difficulty in coordinating care across multiple facilities
   - No remote access to patient data for emergencies

5. **Compliance and Legal Issues**
   - Incomplete surgical consent documentation
   - Difficulty in audit trail creation for legal purposes
   - Challenges in meeting POPIA (Protection of Personal Information Act) requirements
   - Inadequate backup and disaster recovery procedures

### Opportunity for Improvement

Implementing an integrated, multi-hospital management system will:

1. **Enhance Patient Safety**
   - Immediate access to complete medical history
   - Automated allergy and drug interaction alerts
   - Reduced medical errors through standardized workflows

2. **Improve Productivity**
   - 60-70% reduction in administrative time
   - 40% improvement in appointment scheduling efficiency
   - Faster patient check-in and discharge processes
   - Real-time data availability eliminating redundant data entry

3. **Optimize Resources**
   - 25-30% improvement in bed utilization
   - Better surgical theater scheduling increasing utilization by 35%
   - Data-driven staff scheduling reducing overtime costs by 20%
   - Inventory optimization reducing waste by 30%

4. **Increase Revenue**
   - Faster billing and claims processing (50% reduction in payment cycle)
   - Reduced revenue leakage from missed charges (15-20% improvement)
   - Better capacity utilization increasing patient throughput by 25%

5. **Enable Data-Driven Decision Making**
   - Analytics on patient demographics and disease patterns
   - Performance metrics for quality improvement
   - Predictive analytics for resource planning
   - Evidence-based policy making

## 7. MANDATORY FUNCTIONS

The system MUST provide complete CRUD (Create, Read, Update, Delete) operations for all core entities:

### 7.1 User Management

**CREATE (Add/Register)**
- Register new users (patients, doctors, nurses, administrators)
- Create user accounts with role assignment
- Set initial passwords and authentication credentials
- Assign users to specific hospitals

**READ (View/Retrieve)**
- View user profiles and details
- List all users with filtering capabilities
- Search users by name, email, role, or ID
- Display user activity logs
- View user permissions and access levels

**UPDATE (Modify)**
- Update user personal information
- Change user roles and permissions
- Modify contact details
- Update professional credentials
- Change passwords
- Activate/deactivate user accounts

**DELETE (Remove)**
- Deactivate user accounts (soft delete)
- Remove user access permissions
- Archive inactive users
- Maintain audit trail of deleted users

---

### 7.2 Patient Management

**CREATE**
- Register new patients with demographic information
- Create patient medical profiles
- Add emergency contact information
- Generate unique patient identification numbers

**READ**
- View complete patient profiles
- Display patient medical history
- Access patient appointments and consultations
- View patient prescriptions and medications
- Retrieve patient test results
- Display patient allergies and medical conditions

**UPDATE**
- Modify patient personal information
- Update medical history and conditions
- Change emergency contacts
- Update patient allergies
- Modify patient vitals (height, weight, blood group)

**DELETE**
- Deactivate patient records (soft delete)
- Archive old patient files
- Remove duplicate patient entries (with proper verification)

## 8. FUNCTIONAL REQUIREMENTS

### 8.1 User Authentication and Authorization

**FR-1.1**: The system shall allow users to register with email, password, name, role, and contact information.

**FR-1.2**: The system shall authenticate users using email and password credentials.

**FR-1.3**: The system shall generate JWT (JSON Web Token) for authenticated sessions with 30-minute expiration.

**FR-1.4**: The system shall enforce role-based access control with roles: Patient, Doctor, Nurse, Admin, Super Admin.

**FR-1.5**: The system shall allow users to change their passwords securely.

**FR-1.6**: The system shall automatically log out users after 30 minutes of inactivity.

**FR-1.7**: The system shall provide password reset functionality via email.

### 8.2 Patient Management

**FR-2.1**: The system shall allow patients to register with demographic information (name, date of birth, gender, contact details).

**FR-2.2**: The system shall generate a unique patient ID upon registration.

**FR-2.3**: The system shall store patient medical information (blood group, height, weight, allergies).

**FR-2.4**: The system shall allow patients to update their profile information.

**FR-2.5**: The system shall maintain emergency contact information for each patient.

**FR-2.6**: The system shall allow patients to select medical conditions from predefined categories.

**FR-2.7**: The system shall display complete patient medical history to authorized users (doctors, nurses).

**FR-2.8**: The system shall search patients by name, email, ID, or phone number.

### 8.3 Appointment Scheduling

**FR-3.1**: The system shall allow patients to book appointments with doctors by selecting:
   - Hospital
   - Medical condition/reason
   - Doctor (filtered by specialization)
   - Preferred date and time

**FR-3.2**: The system shall display doctor availability in real-time.

**FR-3.3**: The system shall prevent double-booking of appointment slots.

**FR-3.4**: The system shall send appointment confirmation to patients via email/SMS.

**FR-3.5**: The system shall allow patients to reschedule or cancel appointments up to 24 hours before.

**FR-3.6**: The system shall allow doctors to view their daily, weekly, and monthly appointment schedules.

**FR-3.7**: The system shall mark appointments as: Scheduled, Completed, Cancelled, or No-Show.

**FR-3.8**: The system shall filter appointments by status, date range, doctor, or patient.

**FR-3.9**: The system shall calculate and display appointment statistics (total, completed, cancelled, no-shows).

### 8.4 Consultation and Diagnosis

**FR-4.1**: The system shall allow doctors to create consultation records after patient appointments.

**FR-4.2**: The system shall capture: diagnosis, symptoms, physical examination findings, treatment plan.

**FR-4.3**: The system shall link consultations to specific appointments.

**FR-4.5**: The system shall display patient consultation history chronologically.

**FR-4.6**: The system shall allow doctors to add clinical notes and observations.

**FR-4.7**: The system shall track which doctor conducted each consultation.

### 8.5 Prescription Management

**FR-5.1**: The system shall allow doctors to prescribe medications during or after consultations.

**FR-5.2**: The system shall capture for each prescription:
   - Medication name
   - Dosage
   - Frequency
   - Duration (in days)

**FR-5.3**: The system shall link prescriptions to consultations.

**FR-5.4**: The system shall display active and historical prescriptions for patients.

**FR-5.5**: The system shall allow doctors to modify or discontinue prescriptions.

**FR-5.6**: The system shall check patient allergies before prescription creation (alert if conflict).

**FR-5.7**: The system shall generate printable prescription documents.

### 8.6 Surgery Management

   - Patient
   - Surgery type
   - Scheduled date and time
   - Expected duration

   - Surgeon

## 9. NON-FUNCTIONAL REQUIREMENTS

### 9.1 Authentication and Security

**NFR-1.1 Authentication Process**

**Login Sequence:**
1. User navigates to login page
2. User enters email address and password
3. System validates credentials against database
4. If valid:
   - System generates JWT access token (30-minute expiration)
   - System returns token to client
   - Client stores token in local storage
   - User is redirected to dashboard
5. If invalid:
   - System returns error message "Incorrect email or password"
   - User remains on login page

**Logout Sequence:**
1. User clicks logout button
2. System removes access token from client storage
3. User is redirected to login page
4. All active sessions are terminated

**Password Requirements:**
- Minimum 6 characters in length
- Must contain at least one letter
- Passwords are hashed using bcrypt algorithm before storage
- Password reset requires email verification

**Session Management:**
- Session expires after 30 minutes of inactivity
- User must re-authenticate after expiration
- System automatically logs out inactive users

**Security Measures:**
- All passwords stored as bcrypt hashes (never plain text)
- JWT tokens signed with secret key
- HTTPS enforced for all communications in production
- SQL injection prevention through ORM (SQLAlchemy)
- Input validation and sanitization on all user inputs
- Rate limiting on authentication endpoints (max 5 attempts per minute)

### 10.6 Detailed Use Case: Book Appointment

**Use Case Name**: Book Appointment

**Actors**: Patient, System

**Preconditions**:
- Patient must be registered and logged in
- At least one hospital exists in the system
- At least one doctor is available

**Main Flow**:
1. Patient navigates to "Book Appointment" page
2. System displays list of hospitals
3. Patient selects a hospital
4. System displays medical condition categories
5. Patient selects condition category
6. System displays specific conditions within category
7. Patient selects specific condition(s)
8. System displays doctors filtered by specialization matching the condition
9. Patient selects a doctor
10. System displays doctor's available appointment slots
11. Patient selects preferred date and time
12. Patient adds appointment notes/reason (optional)
13. Patient confirms appointment booking
14. System validates appointment slot availability
15. System creates appointment record
16. System sends confirmation email to patient
17. System displays success message with appointment details

**Alternative Flows**:

*3a. No hospitals available*
- System displays "No hospitals available" message
- Use case ends

*10a. No available slots*
- System displays "No available appointments" message
- Patient can select different doctor or date
- Return to step 9

*14a. Appointment slot no longer available (concurrent booking)*
- System displays error message "Slot no longer available"
- Return to step 10

**Postconditions**:
- Appointment is created in database
- Appointment status set to "Scheduled"
- Patient receives confirmation email
- Doctor's schedule is updated

**Special Requirements**:
- Response time: < 2 seconds for each step
- Real-time slot availability checking
- Email sent within 1 minute of booking

### 10.7 Detailed Use Case: Create Consultation Record

**Use Case Name**: Create Consultation Record

**Actors**: Doctor, System

**Preconditions**:
- Doctor must be logged in
- Appointment must exist and be in "Scheduled" or "Completed" status
- Patient must be registered

**Main Flow**:
1. Doctor navigates to patient's appointment
2. System displays patient information and medical history
3. Doctor reviews patient allergies and past consultations
4. Doctor enters diagnosis
5. Doctor records symptoms observed/reported
6. Doctor creates treatment plan
7. Doctor indicates if follow-up is required
8. If follow-up required, doctor sets follow-up date
9. Doctor adds consultation notes
10. Doctor saves consultation record
11. System validates all required fields
12. System creates consultation record linked to appointment
13. System updates appointment status to "Completed"
14. System displays success message

**Alternative Flows**:

*6a. Doctor wants to prescribe medication*
- Include "Prescribe Medication" use case
- Return to step 7

*11a. Required fields missing*
- System displays validation errors
- Return to step 4

**Postconditions**:
- Consultation record created in database
- Appointment status updated to "Completed"
- Consultation linked to doctor and patient
- Timestamp recorded

**Special Requirements**:
- Consultation history must be immediately visible to other doctors
- Audit trail of who created/modified consultation

## 11. TOOLS AND TECHNOLOGIES TO BE USED

### 11.1 Backend Technologies

**Primary Framework**: **FastAPI (Python)**
- **Version**: 0.109.0 or higher
- **Purpose**: RESTful API development, backend business logic
- **Justification**:
  - High performance (async support)
  - Automatic API documentation (Swagger/OpenAPI)
  - Type validation with Pydantic
  - Modern Python features
  - Easy to learn and maintain
  - Excellent for rapid development

**Programming Language**: **Python 3.9+**
- Modern, widely-used language
- Rich ecosystem of libraries
- Strong community support
- Ideal for healthcare applications

**ORM (Object-Relational Mapping)**: **SQLAlchemy 2.0+**
- Database abstraction layer
- Type-safe database operations
- Migration support via Alembic
- Prevents SQL injection attacks
- Supports complex queries

**Database Migration Tool**: **Alembic**
- Version control for database schema
- Automatic migration generation
- Rollback capabilities

### 11.2 Database

**Database Management System**: **PostgreSQL 14+**
- **Justification**:
  - Open-source and free
  - ACID compliance for data integrity
  - Excellent performance for healthcare data
  - Support for complex queries
  - JSON data type support
  - Robust security features
  - Widely used in production environments
  - Strong South African hosting support

**Database Tools**:
- **pgAdmin 4**: GUI for database management
- **DBeaver**: Multi-platform database tool
- **PostgreSQL CLI**: Command-line interface

### 11.3 Frontend Technologies

- **Justification**:
  - Component-based architecture
  - Virtual DOM for performance

  - SEO-friendly (with SSR)
  - Mobile-responsive capabilities

**Programming Language**: **TypeScript 4.9+**
- Static typing for error prevention
- Better IDE support
- Enhanced code quality
- Self-documenting code
- Easier refactoring

**State Management**: **React Query (TanStack Query)**
- Server state management
- Automatic caching

- Easy API integration

**Styling**: **Tailwind CSS 3+**
- Utility-first CSS framework
- Rapid UI development

- Small production bundle size

**HTTP Client**: **Axios**

- Client-side routing
- Nested routes support
